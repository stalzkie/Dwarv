# Decisions

Every non-obvious choice and the reason behind it. Edit entries if the user overrides them; do not delete history, append a new entry noting the change instead.

## Initial decisions (Step 0)

- **OS target**: cross-platform (Windows, macOS, Linux) via a plain `pip install dwarv`. WSL2 is supported but never required. See §2.3 of `DWARV_PLAN.md` for the tiered sandbox this implies.
- **Runtime**: `llama-server` from llama.cpp, over HTTP, one model resident at a time in the MVP. Use the official prebuilt binary release for the host OS/arch; build from source only as a fallback.
- **Language**: Python (3.10+).
- **Internal eval benchmark**: EvalPlus (HumanEval+ / MBPP+) subset, 40 to 60 tasks, frozen (`eval_tasks/subset_v1.json`). Used only to validate the policy; never user-facing — see the 2026-10-09 product-pivot entry below.
- **Models**: Qwen2.5-Coder family, exactly three bundled sizes (see Step 1 of `DWARV_PLAN.md`), never an arbitrary user-supplied model.
- **Package layout**: `src/dwarv`, console script `dwarv`, GUI deps kept in the optional `dwarv[gui]` extra so the core install stays light.
- **Dependency pinning**: minimum-version ranges (`>=`) in `pyproject.toml`, not exact pins, so installs resolve to a wheel that exists for the user's current Python/OS instead of forcing a from-source build. Residual risk: a transitive dependency (e.g. `evalplus`'s own `numpy` bound) can still force a source build on a brand-new Python release; this is upstream and outside `dwarv`'s control — if hit, document it in `docs/PROGRESS.md` rather than fighting it with aggressive overrides.

## 2026-10-09: cross-platform sandboxing, replacing a hard WSL2 requirement

The original plan required Linux/WSL2 because the sandboxed verifier (Step 4) leaned on two Linux-only primitives: `resource.setrlimit` and `unshare -n`. That's real, but it's the *only* OS-specific part of the whole project — `llama-server`, the CLI, and the dashboard are not OS-specific. Decision: keep Linux/macOS's rlimit+`unshare` path, add Docker (`--network none`) as the primary, cross-platform tier, and add a Windows Job Object fallback (reduced isolation, explicitly logged) for native Windows with no Docker. `dwarv doctor` detects and reports which tier is active. Full detail in `DWARV_PLAN.md` §2.3 and Step 4.

## 2026-10-09: product pivot — conversational "local Claude Code," not a benchmark harness

Original framing was a benchmark/research harness first (`dwarv run --task <evalplus-id>`, `dwarv bench`), with the resource-aware controller as the thing being measured. Reframed as a product: `dwarv` with no arguments opens a chat session in the user's own repo, backed by a **fixed, bundled suite of three Qwen2.5-Coder sizes** (never an arbitrary scan of whatever models the user already has — that would break the clean "same family, different size" comparison the policy depends on). At session start, and at every model switch, Dwarv states which model it picked and *why*, using real measured RAM/RSS numbers — this narration is the headline feature, not an internal log line.

Consequences for scope:
- `Task` generalizes from "a frozen EvalPlus problem" to "whatever the user is asking about their own repo." Verification happens by running the repo's own test command (when one is discoverable) in a disposable worktree/temp copy — real files are never touched until a trial change passes there.
- The EvalPlus-based benchmark (baselines A/C/C+, seeds, bootstrap CIs) survives as an **internal eval harness** (`eval/`, `eval_tasks/`, `eval_results/`) that validates the policy during development; it is not a command an end user is expected to run.
- The read-only dashboard (formerly "the GUI deliverable") is now an optional, secondary stretch goal — a `/status` command inside the chat covers the same transparency goal without a server.

Full detail in the rewritten `DWARV_PLAN.md` (all sections). The `src/dwarv` scaffold on disk (from the prior benchmark-first framing: `systems/`, `bench/`, `tasks/`, `results/`, `run`/`bench` CLI subcommands) has **not** been restructured to match yet — that is a separate, explicit follow-up task, not implied by this plan rewrite.

**Update (same day)**: the restructure is done (new `agent/`, `models/`, `repo/` packages; `bench/`→`eval/`; old `systems/` and `src/dwarv/tasks/` removed; `cli.py` now defaults to `chat`). Committed and pushed.

## 2026-10-09: Step 1 real values — llama.cpp build, bundled models, and a disk-space override

Verified against real sources rather than guessed, per the plan's "do not fabricate repo features" rule:

- **llama.cpp**: pinned to numbered release `b11516` (not "latest" — that tag only carries a `nightly-tag.txt`, not binaries; GitHub Actions' `latest` alias doesn't point at a build with real assets for this project). Windows CPU asset is `llama-b11516-bin-win-cpu-x64.zip` (~18MB); Linux/macOS asset names for the same tag are recorded in `configs/models.yaml`'s `llama_cpp.assets` map but not yet downloaded/tested on those OSes. GPU acceleration (CUDA/ROCm/Vulkan builds also exist for this tag) is deliberately skipped for the MVP — matches the plan's risk register ("GPU profiling hard: CPU RAM only; mention GPU as future work").
- **Bundled models**: the official `Qwen/Qwen2.5-Coder-{1.5B,7B,14B}-Instruct-GGUF` repos on Hugging Face, Q4_K_M quant, apache-2.0 licensed. Verified file listing + sizes directly from each repo's file tree (not blog posts) and confirmed byte-for-byte after download: 1.5B = 1,117,320,768 bytes; 7B = 4,683,073,536 bytes; 14B = 8,988,110,272 bytes. Real measured RSS/load time for all three (ctx 4096) are in `configs/models.yaml`.
- **Disk space override**: this dev machine only had 22GB free on `C:` (91% full) against a ~14.8GB total model download — downloading there would have pushed it to ~98% full. Added `DWARV_CACHE_DIR` as an environment-variable override for the cache location (default stays `./cache` inside the project per the plan); for this machine, set to `D:\dwarv-cache` (295GB free). This is a per-machine override, not a new default — `dwarv setup-offline`/`check-offline`/`doctor` all read it via `_cache_dir()` in `cli.py`.
- **Runtime protocol evolution**: `RuntimeAdapter.generate()` changed from a single `prompt: str` to `messages: list[dict[str, str]]` (OpenAI chat-style) — the original protocol code in the plan predates Step 6's explicit multi-turn requirement; using the single-message form under the hood would have silently dropped conversation history once Step 6 is built. Verified live end-to-end against the real small model: load (~2s), a correct chat completion, clean unload, and a second reload with no orphaned process.
- **`check-offline`**: implemented as an automatable proxy for "no network after setup" — loads the small model, generates once, and asserts the server process opened zero non-loopback connections (via `psutil.Process.net_connections()`), rather than requiring the user to physically disconnect networking. This matches the plan's own documented Tier 3 (native Windows, no Docker) fallback: no per-process network kill exists there, so connection-monitoring is the honest substitute. Verified live: passes.

## 2026-10-09: Step 4 — full-file patches instead of model-generated diffs, and Tier 3's real memory guarantee

- **Patches are whole-file replacements, not unified diffs from the model**: `agent/prompts.py` asks the model for the complete new content of each changed file in a `` ```<language>:<path> `` fenced block; `repo/patch.py` computes the unified diff itself (via `difflib`) purely for display. LLMs are reliably good at producing a correct whole file and reliably bad at producing a byte-exact unified diff (off-by-one context lines, wrong line numbers) — asking for a diff would make the "always show the diff before applying" safety property fragile on the generation side instead of just the display side. The diff shown to the user is still real and computed, just never parsed back out of model output.
- **Tier 3's memory limit is a polled watchdog, not a kernel-enforced cap**: a true Windows memory cap needs a Job Object (`CreateJobObject`/`SetInformationJobObject`/`AssignProcessToJobObject`, via `pywin32` or raw `ctypes`). Given the plan already documents Tier 3 as "reduced isolation" and this is explicitly the weakest of the three tiers, implementing the full Win32 Job Object API was deferred in favor of a `psutil`-polled RSS watchdog (checked every 0.1s, kills the process if it crosses the limit) — real and functional, but not kernel-enforced, so a process that allocates a huge block in one shot rather than growing gradually could spike past the limit between polls. This gap is documented in `verify/sandbox.py`'s own docstring, not just here, so it stays visible at the call site.
- **Sandbox tests are tier-forced, not auto-detected**: `tests/test_sandbox.py` forces tier 2 (POSIX) or tier 3 (Windows) rather than letting `sandbox_tier()` auto-select, so CI never depends on Docker being installed or pulling the `python:3.11-slim` image. The network-isolation test auto-detects the real tier and skips with a clear reason on tiers that don't provide network isolation (3, and 2 without `unshare`) — honestly reflects the real per-OS guarantee rather than asserting something that tier can't actually do. Live-verified on this machine (Tier 3): timeout-kill and the memory watchdog both work for real; the network test correctly skips (no Docker here).

## 2026-10-09: two real cross-platform bugs found by CI, not guessed in advance

CI on ubuntu-latest and macos-latest failed on the first push of Step 4 (Windows passed). Both were genuine platform behaviors this dev machine (Windows) could never have surfaced locally — exactly why the cross-platform CI matrix exists:

- **macOS: `resource.RLIMIT_AS` is effectively unusable.** Setting it in `preexec_fn` raised `subprocess.SubprocessError: Exception occurred in preexec_fn` for *every* tier-2 subprocess, even ones that don't touch much memory — dyld's shared-cache mapping needs far more virtual address space at process start than Linux's loader does, so even a conservative limit (2048MB) crashes the child before `exec`. Fix: only set `RLIMIT_AS` when `platform.system() == "Linux"`; `RLIMIT_CPU` (the wall-clock-adjacent limit) is unaffected and still applies on macOS. Consequence: macOS's tier 2 now has no rlimit-enforced memory cap at all, only the wall-clock `timeout_s` via `subprocess.run(..., timeout=...)` — a real, documented gap, not a silent one.
- **GitHub Actions' `ubuntu-latest`: `unshare -n` is installed but not permitted.** `shutil.which("unshare")` found the binary, but running it failed with `unshare: unshare failed: Operation not permitted` — unprivileged network-namespace creation isn't allowed for the `runner` user in that environment. The old code treated "binary exists" as "network isolation works," so every tier-2 command silently got prefixed with a failing `unshare` call and never ran at all. Fix: `unshare_network_available()` actually runs `unshare -n -- true` once and checks it succeeds, used both by `sandbox_tier()`'s reported detail string and by `_run_tier2_posix()`'s decision to prefix the real command — the two can never disagree now.
- A related bug this surfaced: the network-isolation test's skip condition (`"unshare" not in detail`) matched the substring "unshare" inside the *failure* message "no unshare on this OS" too, so the test didn't actually skip on tiers without real isolation — it just silently exercised a non-isolating path and asserted against output that never got the chance to prove anything. Fixed by checking for the literal success marker `"+ unshare -n"` instead of an absence check on a substring that appears in both the success and failure strings.

## 2026-10-09: Step 6 — the model needs repo content included, not just told a test command exists

Live-testing the chat loop against the real small model surfaced a real gap the fake-runtime unit tests couldn't catch (they never involve a real model deciding what to do with incomplete context): the first live run asked Dwarv to "fix the failing test," and it correctly replied asking for the content of `app.py` and `tests/test_app.py` — a sensible response, because the system prompt only told it a test command existed, never what the code actually said. `repo/context.py` gained `snapshot_repo_files()`, a small fenced-block dump of the repo's source files (skipping `.git`/`__pycache__`/etc., bounded by a character budget), appended as a second system message in `agent/session.py`'s `start()`. Re-running the same live scenario afterward: the model correctly identified the one-line bug, proposed a fix, it verified in a real disposable worktree, and got applied for real. This is MVP-scale only — it stuffs matching files into context rather than doing real retrieval/ranking, which won't scale past small repos; documented as a known simplification here and in the function's own docstring, not silently assumed to generalize.

## 2026-10-09: Docker tier is wrong for verifying a user's own repo

The Step 6 push failed CI on ubuntu-latest and windows-latest (macOS passed) with the *fake-runtime* tests running out of scripted responses — a different kind of bug than the earlier Tier 2/3 issues, caught by the same mechanism. The real cause: both of those GitHub-hosted runners have Docker preinstalled, so `verify.sandbox.run()` auto-selected Tier 1 for the repo's test command. Docker's generic `python:3.11-slim` image has none of a real project's installed dependencies — it doesn't even have the test runner itself (`pytest`) — so the sandboxed test run genuinely failed every time, the policy correctly kept retrying, and the test's scripted response list ran out before the retries did. This wasn't a test bug; the verification really was failing, for a reason that has nothing to do with whether the proposed fix was correct.

This exposed a real architectural gap: Docker-tier verification is only meaningful for fully self-contained code with no external dependencies (which is exactly what Step 9's internal EvalPlus eval candidates are) — it cannot usefully run an arbitrary repo's *own* test command, which needs whatever environment the user already has activated (their venv, their installed packages, their actual interpreter). Fix: `verify.sandbox.run()` gained a `skip_docker` parameter: `agent/session.py`'s repo-verification call site now passes `skip_docker=True`, falling through to the native tier (2 or 3) even when Docker is available, since that's the only tier that can see the host/user's real environment. Docker tier remains the default for other future callers (e.g. Step 9's eval harness, not yet built) where self-contained code is the norm.
